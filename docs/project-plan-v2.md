# WayToHome 项目重规划 v2

更新日期：2026-09-29。状态：自动采样与手动记录版本已在本地实现，线上尚未发布。

## 1. 确认范围

项目围绕深圳西丽与衡阳之间的出发前决策，保留两项能力：自动采样、手动预测记录。以当前路况和已录入方案帮助比较走廊与出发时间。

不预留预测 API，不建设预测服务适配层、客户端、权限探测、自动预测刷新、路线自动分类器或相关占位入口。后续实施不以开通预测权限为前提。

需求来源：

- [路线与出发时间联合决策](https://chatgpt.com/s/t_6aab92c1fe008191aac74017382ed3a6)
- [采样价值与节假日样本限制](https://chatgpt.com/s/t_6aab92daac8881919678e984ed9dc6e8)
- 用户于 2026-09-29 确认保留自动采样与手动预测记录，不预留预测接口。

[此前权限核验](forecast-feasibility.md)仅作为历史调查记录，不再作为开发路线图。

## 2. 自动采样

保留当前四走廊、去返方向、对应方向途经点、路线版本隔离及高德普通驾车采样。常规每 30 分钟采样，现有 15 分钟密集档保留配置能力。

采样用于显示当前预计耗时、同轮走廊差距、近期变化、分段路况和同场景历史趋势。文案统一称为“高德在采样时估算的现在出发耗时”，不能称作实跑耗时。

历史记录保留原始日期，并派生日历类型、假期名称、假期阶段和日历规则版本。普通工作日、周末、调休、中秋、国庆及节间日期分开处理；场景样本不足时明确显示。基线同时展示样本数、不同日期数及覆盖时段。

当前 `src/collect.py`、`data/raw/`、来源过滤和版本隔离继续复用。`src/analyze.py` 保留历史分析，现有经验外推出发窗口移出默认决策链，不以普通日样本生成确定的国庆耗时。

## 3. 手动预测记录

用户自行查询后，在看板录入实际看到的方案。记录包括：

| 字段 | 规则 |
|---|---|
| 方向与走廊 | 去程或返程，人工选择四走廊之一；不确定时标为待核验 |
| 预计出发时间 | 完整日期与时间，统一北京时间 |
| 预测行驶耗时 | 正数分钟；录入时可用小时和分钟 |
| 来源与查询时间 | 来源名称和实际查询时间必填；页面链接、截图说明可选 |
| 道路摘要 | 记录主要高速或绕行说明，供确认走廊身份 |
| 费用与备注 | 可选；未提供的费用为空值 |
| 记录标识与修改时间 | 自动生成，用于编辑、删除和导入去重 |

支持新增、编辑、删除及 JSON 导出、导入。首版记录保存在当前浏览器本地，不自动上传公开仓库；页面明确提示不会跨设备同步。导出文件可用于备份和跨设备导入。导入采用预览和字段校验，同 ID 内容冲突时由用户选择保留版本，不静默覆盖。

输入内容按纯文本展示。无效日期、非正耗时及异常文件拒绝导入。来源查询时间晚于记录的预计出发时间时，不能作为出发前预测参与推荐。历史记录可以保存回看。

同一方向、走廊和出发时间允许保留不同查询时刻的记录，默认比较最近一次有效记录，详情展示历史版本。待核验、已过出发时间或超过新鲜度阈值的记录不参加推荐；新鲜度阈值可配置，首版建议 24 小时，并明确这只是提醒复核的产品规则。

手动记录与自动采样分开存储、分开展示，不混入采样基线。只有方向、出发时刻及道路可比时，才展示手动预测与临近出发采样的差异；该差异仍是两次估算之间的差异。

## 4. 比较与页面

页面依次提供行程条件、手动方案比较、当前四走廊路况、历史趋势和路线详情。

- 行程条件沿用现有起终点和候选日期，支持可出发时间、最晚抵达时间和休息时长。
- 手动方案表显示走廊、出发时间、行驶耗时、含休息的预计抵达、来源及查询时间。
- 有多条记录时，可按日期展开路线与出发时间矩阵，缺失格显示“未录入”；不插值、不补经验值。
- 相同出发时刻才做跨走廊耗时比较。不同时间的已录入方案可按条件筛选后排序，称为“已录入方案中用时较少”。
- 只有一条走廊有记录时，不宣称跨走廊最优。未录入任何记录时提供录入入口，当前采样仍独立可用。
- 历史折线图按走廊固定颜色，显示采样日期与场景；图表标题明确是历史参考。
- 地图用于核对道路，不承担主要决策功能。手动记录出现明显绕行时保留备注，不能只凭走廊名称认为路径完全相同。

排名先过滤有效性及行程约束，再按行驶耗时排序。费用未知保持空白，不根据目的地抵达时间直接判定高速免费。原有 `recommended: true` 解释为默认关注走廊，不自动等于最优路线。

## 5. 实现与存储

延续 Python、静态网页和 GitHub Actions。无需新增服务端或数据库。

自动链路保持为普通驾车采样、场景历史分析、`web/data.json` 和看板。手动链路在浏览器内完成录入、校验、本地存储、筛选与展示，不参与 Actions 的数据提交。

建议新增 `src/calendar_tags.py` 统一场景标签；前端独立手动记录模块，定义带版本号的本地数据格式。已有历史记录保持只读兼容，不重写原始文件。现有 `leguang` 走廊 ID 暂时保留，避免名称调整破坏旧记录关联。

继续保留当前 Bark 路况通知的冷却和去重。浏览器手动记录不上传，因此首版不建设基于手动记录的云端通知。

## 6. 实施阶段与验收

| 阶段 | 交付内容 | 验收重点 |
|---|---|---|
| P1 数据语义与趋势 | 场景标签、历史统计、移除默认经验预测 | 去返和路线版本隔离；假期与调休边界正确；自动采样持续运行 |
| P2 手动记录 | 表单、本地保存、编辑删除、导入导出 | 刷新后保留；无效输入被拒绝；冲突可处理；无公开上传 |
| P3 决策看板 | 方案比较、条件筛选、矩阵与当前趋势 | 跨日抵达及休息时长正确；未录入、过期、待核验状态明确；手机可操作 |

必要测试覆盖手动记录存取与导入冲突、方向及时间匹配、数据有效性、条件筛选、跨日抵达和文本安全展示。运行既有采集与通知相关测试及网页冒烟检查，验证改造未破坏自动链路。

先在本地预览新页面，确认数据兼容后再切换正式页面。本轮已实现数据语义、手动记录和页面改造，完成本地测试；采集频率和线上部署未修改。
