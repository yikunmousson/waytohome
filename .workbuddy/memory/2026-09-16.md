## 国庆自驾堵车监测方案（咨询 + 架构设计）

**需求**：实时监测「深圳西丽地铁站 → 目的地（待确认）」固定路线的高速堵车情况，与历史对比，决策国庆出发/返程时间。油车，可全程不停车、可全程夜间驾驶。出发窗口约 9/27–10/1，返程约 10/3–10/7。

**已确认的硬事实（2026 年）**
- 国庆放假 10/1（周四）–10/7（周三），9/20（周日）、10/10（周六）补班。
- 高速免费时段 10/1 00:00 – 10/7 24:00（7 座及以下）。中秋 9/25–27 高速**不免费**。
- 免费判定以**驶离收费站出口时间**为准 → 9/30 全天可上路，10/1 0 点后出高速即免费，可绕开 0 点收费站洪峰。返程须 10/7 24:00 前出高速。

**高德开放平台能力边界（关键结论）**
- ✅ 可用免费：`v5/direction/driving`（全程实时 ETA）；`v3/direction/driving` + `extensions=all` → `tmcs[]` 分段路况（道路名/距离/状态：畅通·缓行·拥堵·严重拥堵/polyline）。个人配额约 5000 次/天、并发 3/s。
- ❌ 不可用：`v4/etd/driving`（高级路径规划 / 未来出行，支持 firsttime+interval+count 最多 48 点、查未来 7 天）**仅企业开发者**，需商务申请。
- ❌ 不提供历史路况。官方历史数据（拥堵延时指数 / 历史拥堵点）为收费企业服务，报价约 7–29 万元/年。
- ⚠️ `v3/traffic/status/{rectangle,circle,road}` 现列为"高级服务接口"，需申请，且只有实时无时间参数。

**方案结论**
- 历史对比必须自建基线（三层）：① 常态基线（出发前 2 周按「周几 × 半小时」聚合）② 节日校准（9/29–10/1 实测 ÷ 基线 = 节日增量系数，再外推假期）③ 先验叠加（往年规律 + 交管/高德免费发布的国庆出行预测报告）。
- 形态选型：**站点为大脑，iOS 小组件为仪表盘**。小组件受 WidgetKit 预算限制（24 小时 40–70 次刷新，≈15–60 分钟一次，系统调度不可控）且不常驻，无法承担采集与趋势展示；但可用 **Scriptable（免费，免 Xcode/免开发者账号）** 写 JS 读 JSON 做速览，且点击小组件会立即重跑脚本 = 手动实时刷新。
- 架构：GitHub Actions（cron `*/15 * * * *`，免费、不需 Mac 常开）采集 → 数据存 repo JSON/CSV → HTML 看板（全程耗时趋势 + 沿线分段路况色带，即"带状热力图"）→ Bark 推送预警。
- 两个必埋的坑：① **路线必须用途经点钉死**，否则高德"躲避拥堵"会自动绕路，分段不可比；② 主数据源优先 `v3` 的 `tmcs`，`v5` 的 `show_fields=cost,tmcs` 部分账号需额外权限。

**待用户补充（阻塞项）**
- 目的地城市（起点已明确为深圳西丽地铁站）。缺此信息无法规划路线、切分关键路段、估算总里程与耗时。
- 候选出发/返程具体日期范围。
- 采集载体确认（建议 GitHub Actions，用户已有 yikunmousson 账号与 Pages 经验）。

## 晚间：多走廊改造（1 推荐 + 3 备选）

**走廊探测（`tests/probe_corridors.py`，新增 `single`/`final` 两个模式）**

改成**单点隔离探测**后才定位到是某些服务区坐标不在主线（或匹配到对向车道）。
判断标准就是里程合理性：本例合理区间 600–730 km。

|---|---|---|---|
| ★ 乐广 G0423 | 黎溪北停车区 `113.272252,23.956502` | 603.2 km / 6.80 h / ¥329 | 627.2 / 6.82 / ¥332 |

**关键结论：默认路线走的就是乐广**（S3广深沿江 → G4京港澳 → S45从埔高速 → 乐广走廊 → 粤北隧道群）。
`bootstrap_geometry` 早先按 OSM 预测的「广连+许广」是错的，实测数据纠正了这个判断。

**模型修正：先验振幅按里程位置衰减（重要）**
原模型推出「凌晨 2 点 5.1 小时跑完 603 km」= 均速 118 km/h 含隧道群，物理不可能。
根因：把城市道路的日形状（晚高峰 +39%）套到了整条 600 km 长线上，但 80% 是山区高速。
修正：`URBAN_KM=60`、`RURAL_AMP=0.22`、`MAX_AVG_SPEED=115`；
起终点 60 km 内保留 100% 振幅，中间纯高速只留 22%；逐段按各自位置取振幅。
结果：乐广畅通基准 5.1 h → **6.0 h**（均速 100 km/h），与常识一致。

**数据卫生修复（重要）**
`build_baseline()` 之前没有按 `source` 过滤 —— 仿真数据会污染真实基线。
现在 `analyze.py` 入口统一用 `usable(rec, cfg)` 过滤，基线/推算/分段全用它；
开关 `analysis.include_simulated`（默认 false）。旧 `routes` 格式记录自动迁移到推荐走廊名下。

**代码结构变化**
- `config.yaml`：`trip.corridors` / `return_trip.corridors` 列表取代单个 `waypoints`；
  `collect.strategy: 0`（速度优先）取代 `strategies: [5,0]`
- `collect.py`：遍历走廊采集，移除 `write_latest`（data.json 只由 analyze.py 产出，单一数据源）
- `analyze.py`：全面重写为多走廊（每走廊独立基线 / 独立窗口推算 / 跨走廊对比 `now_table`+`best_overall`）

  热力图走廊切换（默认"最快走廊"）、每条走廊自己的最优窗口表、走廊×20 段均速矩阵、
  分段色带改为**按里程占比堆叠**（原来取占比最高状态会把"48%畅通+52%拥堵"画成全绿）
- `widgets/scriptable-widget.js`：多走廊版（4 行一览 + 最佳窗口）
